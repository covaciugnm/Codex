# Plan pentru iPhone ca sistem perceptiv al unui humanoid

Data: 6 octombrie 2026, Europe/Bucharest. Versiunea 1, propunere pentru audit.

Scopul este extinderea EVA 3DScan pentru scanare de camere și obiecte, localizare persistentă, recunoaștere multimodală, navigare și manipulare cu un humanoid, plus cooperare între mai multe telefoane și roboți. Livrarea acestei etape este documentația de implementare. Instalarea pe telefoane/server și testele fizice sunt etape următoare.

## Decizia de arhitectură

iPhone-ul deține captura, VIO, percepția locală și interacțiunea. Calculatorul robotului deține estimarea corpului, TF, planificarea locală, echilibrul și actuarea. Serverul comun execută modele grele, optimizează hărțile, păstrează istoricul și distribuie revizii ale lumii. Toate cele trei niveluri trebuie să funcționeze cu întreruperi de rețea și cu date explicit învechite.

„La maxim” înseamnă catalog extins de metode și alegerea celei mai capabile pentru sarcină pe baza măsurătorilor. Modelele nu rulează toate simultan: bugetele termice, memoria, latența și concurența camerei sunt resurse partajate. Capacitatea de stocare de 1 TB nu este memorie de inferență.

## Captură și selecție de metode

Un CaptureCoordinator deține ARSession și publică pachete imuabile RGB/depth/intrinsics/pose/timestamp/confidence. Consumatorii pentru obiecte, persoane, gesturi și recording au cozi proprii limitate. Se păstrează intrinseci și transformarea crop/resize; pixelul detectorului trebuie să corespundă pixelului de adâncime. RGB-only video nu permite reconstruirea retrospectivă garantată a pozițiilor metrice.

Matricea de capabilități se generează pe dispozitiv: configurații ARKit, LiDAR/depth, mesh, TrueDepth, camere simultane, rezoluții, termic, audio, limbi și modele disponibile. Un profil de montaj precizează orientarea telefonului, extrinseca spre cap și cablarea. Camerele telefonului sunt rigid legate; o hartă acumulată prin rotire nu este vedere simultană la 360 grade.

Specialistul iOS verifică separat API-urile din iOS 27, inclusiv Core AI, Foundation Models și object tracking, față de Core ML/ARKit existente. Fiecare noutate intră prin adaptor și feature flag; lipsa modelului, a limbii ori a capabilității produce fallback verificabil.

Pentru viziune, păstrăm detectorul actual ca baseline și comparăm detectoare compacte, segmentare pe instanță, embeddings, tracking temporal și estimare 6DoF. Metodele grele au endpoint pe server. Alegerea finală cere benchmark comun; clasamentele publice nu dovedesc performanța pe obiectele și lumina acestui proiect.

## Memoria spațială și roboții colaboratori

Entități: site, floor, room, robot, sensor, observation, object instance, person, map revision, calibration, task. Observațiile sunt imuabile; estimările sunt revizuibile. Obiectele au UUID global, aliasuri locale și istoric; relațiile on/in/near/held_by au sursă, timp, încredere și expirare.

Robotul R publică în namespace propriu. Lanț conceptual: map comun → odom_R → base_link_R → articulații → head_R → phone_R → optical_R. O singură autoritate per muchie TF. VIO nu se dublează ca măsurare independentă cu IMU-ul deja folosit în aceeași estimare. Mișcarea gâtului cere joint states la capture time.

Fiecare robot pornește într-un submap local și se aliniază la hartă prin repere geometrice/fiduciale și potriviri verificate. Nu deducem alinierea din numele camerei. Serverul verifică consistența geometrică, menține ipoteze pentru locuri repetitive și emite transformări versionate. ARKit collaborative session poate sprijini pilotul local, dar nu înlocuiește harta semantică multi-robot durabilă.

Evenimentele au idempotency key și proveniență. Conflictele de identitate nu se rezolvă prin last-write-wins. Fuziunea nu numără aceeași observație retransmisă de două ori. Disconectarea păstrează submap și jurnal local; reconnect cere handshake, revizii, delta sau snapshot cu hash și aplicare atomică. Harta comună nu este suficientă pentru evitarea coliziunilor între roboți: rezervarea sarcinilor și spațiilor are leasing și expirare; controlul local rămâne autoritar.

## Server și instalări planificate

Servicii separate: gateway autentificat; catalog modele; inference workers pentru segmente/pose/ASR; world-model API și PostgreSQL; object storage pentru RGBD/hărți; queue de joburi; optimizare map; observabilitate și backup. Worker-ul video existent se extinde cu job lease, heartbeat, retry și rezultate per instanță, legate de timestamp/depth/pose. O simplă listă de clase din MP4 nu actualizează automat inventarul 3D.

Profilele hardware se aleg după inventarierea serverului. CPU-only susține stocare/control și joburi offline; GPU de dezvoltare execută batch limitat; serverul multi-GPU separă workload live și reconstruire/LLM. VRAM și throughput nu se promit înainte de măsurare. Intrările RGBD, obiectele rare și cazurile cu incertitudine mare sunt prioritizate pentru offload; fallback local rămâne disponibil.

Instalare în implementare: inventar hardware → pin versions și licențe → mediu staging separat → backup/migrare DB → containere cu limite → modele cu checksum → probe API → replay → canary pe un robot → doi/patru roboți → rollback testat. Nicio comandă de instalare nu a fost rulată pe serverul operațional în etapa de planificare.

## Persoane voce gesturi și LLM

Fața, diarizarea, identificarea vorbitorului și transcrierea sunt rezultate diferite. Un PersonTrack le asociază temporal/spațial și păstrează ipoteza necunoscută. Enrollment și pragurile se calibrează pe persoane/medii distincte de test; embeddings din motoare diferite nu se compară direct. Sincronizarea biometrică urmează opțiunea utilizatorului și ștergerea se propagă către cache-uri și dispozitive.

AudioCoordinator gestionează VAD, captură, TTS, anulare ecou și barge-in. STT română/engleză se compară local și server pe zgomotul robotului. SpeechAnalyzer și alternativele se califică pe limbă, nu doar existența API. Gesturile încep cu indicare, chemare, oprire și confirmare; interpretarea temporală evită declanșările dintr-un singur cadru. Gestul vocal/vizual de oprire este suplimentar controlului fizic independent.

LLM-ul citește context bounded cu UUID, reper, prospețime și incertitudine. Acțiunile sunt tipate: find_object, inspect_object, navigate_to, pick_object, place_object. Executorul verifică precondiții, timeouts, anulare, exclusivitate și postcondiții; retry la pick nu dublează comanda fizică. Notele/OCR/vorbirea sunt date externe, nu instrucțiuni pentru a schimba regulile executorului. Model local mic plus server mai capabil se compară pe aceleași sarcini.

## URDF și utilizarea robotului

RobotProfile conține URDF rezolvat din XACRO, mesh-uri, unități, joint limits, inerții, collision geometry, SRDF, controlere și calibrarea telefonului. XACRO se rezolvă într-un mediu controlat și se exportă un pachet verificat pentru iPhone. Vizualizarea modelului nu înseamnă control. Navigarea globală folosește camere/uși; mersul humanoid cere suprafețe de sprijin și geometria întregului corp. Manipularea cere obiect reobservat, pose validă, grasp candidate, collision check și confirmare de contact.

## Acceptare și riscuri deschise

Date de test separate pe camere, obiecte, persoane și sesiuni; nu împărțim cadre aproape identice între train/test. Raportăm p50/p95/p99, erori, indisponibilitate, ID switches, reseturi, consum și termic. 6DoF se evaluează pe simetrii și pe cerințele taskului. Pentru pilot, țintele din dosarul existent 30 mm/5 grade și 100 ms rămân exploratorii, nu toleranțe de prindere sau mers validate.

Aspecte încă de completat în versiunea următoare: matrice nominală de metode moderne cu surse și licențe; compatibilitate SDK/OS; schema wire și map merge detaliată; pași operaționali și praguri complete; cost/resource sizing; audit independent al întregului pachet. Modelul robotului și hardware-ul serverului nu sunt furnizate încă. R0 le rezolvă înaintea comenzilor dependente de hardware.
