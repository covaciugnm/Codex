The real bulk materialization stopped on case-insensitive filename collisions. Independent inspection found 77 collision pairs in each of the four vendor Translate variants, four in AINOTE, none in Bavvo/Loomy/the derived APKs, and no file-versus-directory prefix collisions in these actual inputs. Evidence: `case-collision-inputs.json`.

The implementation must use deterministic physical path mapping with a reversible `PATH-MAP.json`, retain original logical paths and hashes, preserve every distinct byte sequence and prove that no stale files remain from interrupted attempts. Final closure requires independent collision fixtures and full Translate verification after the fix, followed by all-variant materialization success.

The old Translate raw extraction has 2,264 physical file records, while the same original APK contains 2,341 files and zero directory entries. Exactly 77 case-alias pairs explain this discrepancy; all 77 pairs contain different bytes. Comparison by exact logical name found 77 missing paths and 75 present paths whose recorded bytes belong to the other case alias. The old README's explanation that the difference consists of directories is incorrect.

Evidence: `baseline-case-loss.json`, including every affected pair and hash comparison. Existing raw files can still be reused **by verified content hash** even where their old path label is wrong. The new raw manifests already retain every original entry correctly; the remaining fix concerns physical Windows path materialization. The old raw tree must not be described as a complete byte-accurate logical extraction.
