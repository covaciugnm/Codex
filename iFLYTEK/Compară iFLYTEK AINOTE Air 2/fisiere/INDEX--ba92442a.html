1. Straturile comunicației

Flutter comunică în interiorul aplicației cu pluginurile Android prin MethodChannel/EventChannel. Pluginurile folosesc GATT pentru controlul ochelarilor și unele fluxuri audio; Wi-Fi Direct și TCP pentru fișiere/OTA; gRPC peste TLS pentru serviciile cloud. Codecurile, cadrele BLE și mesajele gRPC sunt niveluri diferite.

UI Flutter/Dart
  └─ MethodChannel / EventChannel
      ├─ BLE GATT → comenzi JSON în cadre binare / audio / notificări
      ├─ Wi-Fi Direct → TCP → cadre binare / fișiere / OTA
      └─ TLS + HTTP/2 + gRPC → JSON sau JSON + audio binar
          └─ STT / traducere / TTS / alte funcții AI

3. Cadrul binar comun

Antetul are 14 octeți. Câmpul length include payload-ul și octetul final CRC; lungimea totală este 14 + length.

OffsetLungimeCâmp și reprezentare
04Magic: AA FF 55 00
44handle: 00 00 00 00 în constructorii observați
81version
91opCode: 1 request, 2 response, 3 indication, 4 notification
102sequenceId, little-endian; contorul de cadru pornește de la 0
122length, little-endian; payload + CRC
14variabilpayload; începe cu moduleID și msgID
ultimul1CRC-8: polinom 0x07, init 0, fără reflexie, xor final 0

Terminologia din raportul inițial este corectată: offsetul 9 este opCode, nu canal audio; offsetul 14 este moduleID, iar offsetul 15 este msgID. Pentru JSON, moduleID=1 și msgID=1 în builderul analizat. CRC se calculează pe toți octeții anteriori lui. Echivalent, implementarea Wi-Fi verifică CRC pe întreg cadrul și așteaptă rezultatul zero.

ProtocolHeader · Constante cadru · CRC · Reasamblare BLE.

O notificare BLE nu trebuie confundată cu un cadru complet. gf0 acumulează fragmente, folosește magic pentru început și compară lungimea acumulată cu antetul. Dispatcherul său transmite opCode=2 către răspunsuri și opCode=4 către notificări. Parserul observat nu este un parser generic robust pentru orice concatenare de cadre; un SDK nou trebuie să trateze explicit cadrele fragmentate, concatenate și lungimile invalide.

4. Comenzi JSON și răspunsuri

Schema comună BLE: opt (operație), optNum (identificator comandă), biz_num (identificator logic) și parametrii funcției. sequenceId din antet este un contor separat. optNum începe la 1 și revine la 1 după 65535; sequenceId revine la 0. În răspunsuri, errCode=0 este tratat ca succes în numeroase handlere. Rezultatul complet depinde de opt; nu există o schemă universală de răspuns pentru toate dispozitivele.

5. Payload audio

Parserul efectiv din Bluetooth este m07 (PayLoadEarAudio), apelat pentru moduleID 2 sau 4. Varianta este selectată din versiunea cadrului primit, nu presupusă din versiunea cadrului de comandă emis.

Versiune primităLayout payload, începând de la offsetul global 14
1 și alte valori decât 2/3moduleID:1 | msgID:1 | type:1 | chunk:4 big-endian | audio:N
2moduleID:1 | msgID:1 | type:1 | cr:1 | chunk:4 big-endian | audio:N
3moduleID:1 | msgID:1 | type:1 | compressionRate:1 | bizId:2 big-endian | chunk:4 big-endian | audio:N

Endianness diferă intenționat: antetul este little-endian, în timp ce m07 citește chunk cu ml0.b în big-endian. CoreBluetoothDevice extrage și octetul superior al chunk pentru contabilizarea pierderilor; nu interpreta automat acest câmp ca un simplu număr monoton de pachet.

typeSens din aplicație
0default
1 / 2left ear / right ear
3 / 4near end / far end
5 / 6glass self / glass other

Acestea sunt etichete logice, nu dovada a șapte microfoane fizice. Decoderul Opus analizat lucrează la 16 kHz, cu căi mono și stereo și ieșire PCM signed 16-bit little-endian. Câmpul cr selectează și blocuri de 40/80/160 octeți în anumite căi. Maparea completă codec/rată/mod necesită verificarea versiunii și captură audio.

Există separat PayLoadAudio în pachetul Wi-Fi: moduleID, msgID, chunk BE pe 4 octeți și date cu lungime multiplu de 128. Acest parser are alt layout decât m07. În sensul telefon→ochelari, zb0.L1 folosește opCode=3, moduleID din profil (2), msgID=1 și un blob audio primit de la apelant; nu introduce automat headerul audio de recepție.

6. Wi-Fi Direct, TCP, fișiere și OTA

Aplicația creează/conectează rețeaua P2P și trimite configurarea prin BLE. Builderul h1 include encryption="wpa2". Fluxul startGlassWifi folosește wifiType=0, wifiBand="5" și canal 0; acestea sunt valori ale acestei căi, nu garanții pentru orice firmware.

{

  "optNum": 2,
  "biz_num": 0,
  "ctrl": 1,
  "ssid": "<SSID>",
  "wifiType": 0,
  "pwd": "<PAROLA_WIFI>",
  "wifiBand": "5",
  "wifiChannel": 0,
  "encryption": "wpa2"
}

connectSocket$lambda$6 conectează un socket TCP la IP-ul primit și portul 6688, cu timeout de conectare de 5 s. Portul 8888 apare într-o cale de server/test; nu este dedus ca port principal al ochelarilor. Sunt folosite Socket/Network socket factory; nu apare un strat TLS în această cale locală. Protecția rețelei WPA2 este un nivel separat.

Conectarea și transferul · Constanta port 6688 · WifiFrameBuilder.

TCP transportă aceleași cadre AA FF 55 00, nu un document JSON delimitat prin newline. Pentru fișiere, payload-ul modulului 3 are următoarea structură:

Cadru total: N+26; length=N+12. Structura nu este același lucru cu forma specială AlgoOtaChunk: moduleID=3, msgID=1, type:1, curChunkNum:4 LE, isLastChunk:1, date; în acea variantă cadrul are N+23. Nu se amestecă cele două formate.

Formatul mesajelor cloud

gRPC standard adaugă un octet pentru compresie și o lungime big-endian pe 4 octeți înaintea mesajului. Cadrul HTTP/2 este un nivel exterior și poate fragmenta mesajul. Specificația gRPC.

HTTP/2 DATA
└─ gRPC: compressedFlag:uint8 | messageLength:uint32BE | MESSAGE

MESSAGE pentru clasele care NU extind Buffer:
  JSON UTF-8

MESSAGE pentru clasele care extind Buffer:
  jsonLength:uint32BE | JSON UTF-8 | date binare rămase

Nu se adaugă CRC-ul BLE la un mesaj gRPC.

Marshallerul k36 verifică moștenirea Buffer. mData este transient și se scrie separat de JSON; nu este codificat automat Base64. Prefixul JSON folosește mi0.writeInt, verificat big-endian. Clasele audio și unele răspunsuri moștenesc Buffer; cererea TxtTransRequest nu îl moștenește.

MixMarshaller · readInt/writeInt · Buffer.

Răspunsuri

ResponseType definește iat, its, tts, ocr și ctr. AudioTransResponse/LongAudioTransResponse includ c (cod), d (descriere), t (tip), r (rezultat), s (sesiune), l (sfârșit), pgs, textstart/textend/textserial, iatresulttime și alte câmpuri. Dacă răspunsul extinde Buffer, datele audio sunt după JSON în payloadul binar. BlcUtils consideră codul string "000000" succes; acesta diferă de errCode=0 din BLE și de grpc-status=0 din transport.

10. Verificări, limite și integrare

Verificate local: fixture-ul baterie din SDK, CRC-8 pe cadru, existența surselor și legăturilor. Nu au fost efectuate accesări cloud autentificate, comenzi BLE, transferuri sau OTA. Pentru un client interoperabil rămân de verificat pe modelul/firmware-ul real: capabilitățile GATT, MTU, asocierea/activarea, succesiunea exactă HELLO/configurare, versiunea payloadului audio, răspunsurile reale și credențialele obținute legitim prin cont.

Acoperirea este a traseelor ochelari–aplicație și traducere analizate. SDK-urile de plăți, telemetrie și dependențele Android incluse în APK nu sunt specificate integral aici. Sursele Dart AOT, codul firmware și backendul nu sunt complet vizibile; nu afirm că documentul este întregul protocol proprietar al producătorului.
